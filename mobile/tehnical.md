## 🔴 Высокий приоритет (Влияет на стабильность и поддержку)

### 1. Автоматическое тестирование офлайн-логики

**Проблема:** В проекте отсутствуют Unit-тесты. Офлайн-синхронизация (`SyncManager`) и работа с IndexedDB — это сложные асинхронные процессы с ретраями, таймаутами и состояниями гонки. Любая ошибка в логике очереди может привести к потере данных механиков.
**Решение:**

- Внедрить тестовый фреймворк (Vitest или Jest).
- Покрыть тестами `SyncManager` и `OfflineDB`.
- Обязательно протестировать сценарии: обрыв связи в середине цикла отправки, идемпотентность запросов, таймауты API.
- Для тестов IndexedDB использовать `fake-indexeddb`.

### 2. Уведомление об обновлении Service Worker

**Проблема:** Сейчас новый SW активируется через `self.skipWaiting()`. Если структура данных в IndexedDB изменилась (как это было при переходе на версию 2), старая версия вкладки может работать некорректно с новой базой, или пользователь просто не знает, что вышло обновление.
**Решение:** Добавить в `main.js` слушатель события `controllerchange`, который будет показывать пользователю тост: _«Доступно обновление приложения. Перезагрузить?»_.
_Пример реализации в `main.js`:_

```javascript
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.addEventListener('controllerchange', () => {
    // Показываем кастомный тост или модалку
    ui.confirm("Доступна новая версия приложения. Перезагрузить сейчас?", "Обновление").then((yes) => {
      if (yes) window.location.reload();
    });
  });
}

3. Рефакторинг работы с DOM и шаблонизация
Проблема: Контроллеры (особенно ListController и CardController) активно используют прямые DOM-запросы (document.querySelector) и конкатенацию HTML-строк (innerHTML). При росте сложности интерфейса это приведет к дублированию кода, снижению производительности парсинга и усложнит поддержку.
Решение:

Вынести кэширование DOM-элементов в constructor контроллеров (чтобы не искать их при каждом рендере).

Для рендеринга списков использовать нативный тег <template> в index.html или внедрить легковесный шаблонизатор (например, lit-html), чтобы полностью отделить HTML-разметку от JS-логики.

🟢 Низкий приоритет (Косметика и Developer Experience)
4. Управление глобальным состоянием
Проблема: Состояние сессии (authStore) и синхронизации (syncManager) размазано по singleton-объектам и localStorage.
Решение: При дальнейшем росте приложения рассмотреть внедрение легковесного стейт-менеджера (например, Proxy-based, как valtio или нативный EventTarget), чтобы компоненты могли реактивно подписываться на изменения статуса сети или сессии.

5. Оптимизация сборки
```
