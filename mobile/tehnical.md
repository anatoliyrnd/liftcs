# 📝 Технический долг (Technical Debt) — Мобильное приложение «ЛК Механика»

**Дата создания:** 25.10.2026
**Статус:** Актуально
**Связанные документы:** API_PROTOCOL.md, AUTH_PROTOCOL.md, OFFLINE_PROTOCOL.md

Этот документ фиксирует известные архитектурные компромиссы, временные решения и задачи по рефакторингу, которые необходимо выполнить при дальнейшем развитии проекта. На текущий момент приложение полностью функционально, но имеет критические зоны роста в области безопасности, офлайн-синхронизации и масштабируемости.

## 🔴 Высокий приоритет (Влияет на стабильность и безопасность)

### 1. Безопасность: уязвимость с токеном в localStorage

**Проблема:**
В `auth-store.js` задокументировано, что access-токен хранится **только в памяти** для защиты от XSS-атак. Однако в `main.js` реализован механизм восстановления сессии после перезагрузки:

```javascript
const offlineToken = localStorage.getItem("mob_offline_token");
if (offlineToken) {
    authStore.setSession(offlineToken, ...);
}
Если mob_offline_token является полноценным access-токеном, его запись в localStorage полностью обесценивает защиту от XSS. Любой вредоносный скрипт, попавший в приложение, сможет украсть токен.
Решение:
Полностью отказаться от хранения токенов в localStorage/sessionStorage.
Перейти на авторизацию через httpOnly cookies (см. пункт 3).
Если офлайн-токен необходим для работы в фоне, он должен быть зашифрован и иметь минимальные права (только чтение кэша).
2. Миграция IndexedDB: потеря данных при обновлении
Проблема:
В offline-db.js при повышении версии базы данных происходит безвозвратное удаление хранилища очереди:
javascript
if (!db.objectStoreNames.contains("sync_queue")) {
    db.createObjectStore("sync_queue", { keyPath: "uuid" });
} else {
    db.deleteObjectStore("sync_queue"); // ⚠️ УДАЛЕНИЕ ДАННЫХ
    db.createObjectStore("sync_queue", { keyPath: "uuid" });
}
Если у механика накопились неотправленные действия в очереди (работа в офлайне), и в этот момент приложение обновится, все несохранённые заявки будут потеряны.
Решение:
Реализовать безопасную миграцию данных:
При обновлении версии БД создать новое хранилище (например, sync_queue_v2).
В транзакции upgrade прочитать все записи из старого хранилища.
Записать их в новое хранилище.
Удалить старое хранилище только после успешного переноса.
Обновить все ссылки на имя хранилища в коде.
Альтернатива: Использовать библиотеку миграций (например, idb с поддержкой версионирования) или хранить версию схемы в config и мигрировать поэтапно.
3. Переход на httpOnly cookies для авторизации
Проблема:
Текущая схема с access-токеном в памяти и refresh-токеном в httpOnly cookie работает, но имеет сложности:
Необходимость в мьютексе на обновление токена.
Уязвимость с localStorage (см. пункт 1).
Сложность поддержки многодевайсного входа.
Решение:
Перейти на единый токен авторизации в httpOnly cookie сроком на 30 дней.

Жизненный цикл:
Пользователь входит по паролю → сервер создаёт сессию → устанавливает httpOnly cookie.
При каждом запросе браузер автоматически отправляет cookie.
Сервер проверяет токен + device_id + expires_at.
При выходе сервер удаляет сессию из БД и очищает cookie.
Сервер может принудительно отозвать любую сессию в любой момент.
Привязка к устройству:
Каждая сессия привязана к device_id. При каждом запросе сервер проверяет, что отпечаток устройства совпадает с сохранённым в сессии. Это защищает от использования украденного токена с другого устройства.
4. Автоматическое тестирование офлайн-логики
Проблема:
В проекте отсутствуют Unit-тесты. Офлайн-синхронизация (SyncManager) и работа с IndexedDB — это сложные асинхронные процессы с ретраями, таймаутами и состояниями гонки. Любая ошибка в логике очереди может привести к потере данных механиков.
Решение:
Внедрить тестовый фреймворк (Vitest или Jest).
Покрыть тестами SyncManager и OfflineDB.
Обязательно протестировать сценарии:
Обрыв связи в середине цикла отправки.
Идемпотентность запросов (повторная отправка не создаёт дубли).
Таймауты API и обработка AbortError.
Конфликт версий данных при синхронизации.
Для тестов IndexedDB использовать fake-indexeddb.
5. Безопасное обновление Service Worker
Проблема:
Сейчас новый SW активируется через self.skipWaiting() в install и self.clients.claim() в activate. Это приводит к проблеме:
Новый SW скачивается в фоне и мгновенно активируется.
clients.claim() принудительно переводит старую вкладку под управление нового SW.
Пользователь видит модалку «Перезагрузить?», но если нажимает «Не сейчас», страница продолжает работать со старым JS-кодом, но под управлением нового SW.
Если изменились имена кэшей или логика fetch, старая вкладка может сломаться.
Решение:
Перейти на управляемый паттерн обновления:
Изменения в sw.js:
Убрать self.skipWaiting() из install.
Добавить обработчик сообщений:
javascript
  self.addEventListener('message', (event) => {
      if (event.data === 'SKIP_WAITING') {
          self.skipWaiting();
      }
  });
Изменения в main.js:
Слушать событие updatefound на объекте registration.
Когда новый SW переходит в состояние installed и есть активный контроллер — показать модалку.
При согласии пользователя отправлять reg.waiting.postMessage('SKIP_WAITING').
Слушать controllerchange для финальной перезагрузки.
Дополнительно: Перед перезагрузкой сохранять черновики пользовательского ввода в sessionStorage, чтобы не терять несохранённые данные (см. пункт 12).

6. Многодевайсная авторизация
Проблема:
Пользователь должен иметь возможность работать на нескольких устройствах одновременно (телефон, планшет, ПК). Текущая схема с одним токеном не поддерживает независимые сессии на разных устройствах.
Решение:
Архитектура сессий с привязкой к устройствам (расширение пункта 3).
Ключевые принципы:
Одна сессия = одно устройство.
Вход на новом устройстве создаёт новую сессию, не удаляя старые.
Выход с устройства удаляет только текущую сессию.
Лимит активных устройств: 5 на пользователя. При превышении самая старая (по last_activity) сессия удаляется автоматически.
Таблица user_devices (вспомогательная):
Поле
Назначение
user_id
Пользователь
device_id
Отпечаток устройства
device_name
Имя устройства
last_used
Когда устройство использовалось в последний раз
Функции управления сессиями (в профиле):
Список активных устройств с датой последней активности.
Завершение сессии на конкретном устройстве.
Завершение всех сессий кроме текущей.
Сценарий использования:
Пользователь входит на телефоне → создаётся сессия №1.
Пользователь входит на планшете → создаётся сессия №2.
В профиле телефона видно оба устройства.
При потере планшета пользователь может завершить его сессию удалённо.
7. Push-уведомления
Проблема:
Механики не узнают о новых заявках, если приложение закрыто. Текущий polling работает только при открытом приложении.
Решение:
Внедрить Web Push через протокол VAPID.

Подписка может «протухнуть» → при ошибке 404/410 удалять из БД.
8. Оптимизация API: получение заявки по ID
Проблема:
В CardController.loadData() при отсутствии заявки в локальном кэше контроллер скачивает весь список открытых заявок, а затем весь список закрытых, чтобы найти одну нужную по id. Это создаёт избыточный трафик и нагрузку на сервер.
Решение:
Добавить на бэкенд эндпоинт для получения конкретной заявки по её идентификатору:
POST /api.php
{
    "data": "ticket_detail",
    "id": 12345
}
Алгоритм работы CardController.loadData() после оптимизации:
Проверить заявку в локальном кэше IndexedDB.
Если не найдена → запросить ticket_detail по ID.
Если сервер вернул заявку → сохранить в кэш и отобразить.
Если сервер вернул 404 → показать «Заявка не найдена».
Преимущества:
Снижение трафика в 10–100 раз (в зависимости от размера списков).
Ускорение открытия карточки заявки.
Снижение нагрузки на сервер.
9. Рефакторинг работы с DOM и шаблонизация
Проблема:
Контроллеры (особенно ListController и CardController) активно используют прямые DOM-запросы (document.querySelector) и конкатенацию HTML-строк (innerHTML). При росте сложности интерфейса это приведёт к:
Дублированию кода.
Снижению производительности парсинга.
Усложнению поддержки.
Рискам XSS при недостаточном экранировании.
Решение:
Вынести кэширование DOM-элементов в constructor контроллеров (чтобы не искать их при каждом рендере).
Для рендеринга списков использовать нативный тег <template> в index.html или внедрить легковесный шаблонизатор (например, lit-html), чтобы полностью отделить HTML-разметку от JS-логики.
Все пользовательские данные экранировать через escapeHtml() (уже используется, но нужно сделать обязательным для всех мест).

10. Управление глобальным состоянием
Проблема:
Состояние сессии (authStore) и синхронизации (syncManager) размазано по singleton-объектам и localStorage. Компоненты не могут реактивно подписываться на изменения статуса сети или сессии.
Решение:
При дальнейшем росте приложения рассмотреть внедрение легковесного стейт-менеджера (например, Proxy-based, как valtio, или нативный EventTarget), чтобы компоненты могли реактивно подписываться на изменения:
Статуса сети (online/offline/syncing).
Статуса авторизации.
Очереди синхронизации.
11. Оптимизация сборки
Проблема:
Сейчас файлы отдаются как есть (ES-модули). Много мелких HTTP-запросов при первой загрузке. Нет минификации и автоматического хэширования.
Решение:
Внедрить сборщик (Vite или Rollup) для:
Минификации CSS/JS.
Объединения модулей в бандлы.
Автоматической генерации хэшей (cache busting) для продакшена.
Tree-shaking неиспользуемого кода.
Интеграция с Service Worker:
После внедрения сборщика обновить sw.js для кэширования бандлов с хэшами в именах файлов.
12. Сохранение черновиков при обновлении
Проблема:
При window.location.reload() во время обновления приложения теряется несохранённый пользовательский ввод (черновики комментариев, решения по заявкам).
Решение:
Перезагрузкой страницы сохранять критичные поля ввода в sessionStorage:
Алгоритм:
Перед отправкой postMessage('SKIP_WAITING') вызывать saveDrafts().
saveDrafts() находит все активные поля ввода и сохраняет их значения в sessionStorage с ключом, привязанным к ticket_id.
После перезагрузки контроллеры при mount() проверяют наличие черновиков и восстанавливают их.
После успешной отправки или закрытия карточки черновики удаляются.
Пример ключей:
draft_comment_{ticketId}
draft_solution_{ticketId}
13. Уведомления о новых входах (безопасность)
Проблема:
Пользователь не узнает, если кто-то войдёт в его аккаунт с нового устройства.
Решение:
При создании новой сессии на незнакомом устройстве отправлять уведомление пользователю на все остальные устройства:
Триггер: Создание новой записи в user_sessions, если device_id ранее не встречался в user_devices.
Данные уведомления:
type: "new_login"
device_name — имя нового устройства
ip_address — IP входа
created_at — время входа
Действие клиента: Показать уведомление с кнопкой «Это не я», которая ведёт в профиль для завершения подозрительной сессии.
