2. Зафиксированные архитектурные решения
2.1. Address Service
Центральный Address Service — отдельный сервис (не модуль). Обоснование: тенантские бэкенды могут оказаться за периметром, реквизиты Master DB нельзя раздавать.

Роль центрального сервиса: резолвер имён (batch ID → имена) + глобальная версия имён. Не собирает список адресов организации.

Список адресов организации собирает тенантский бэкенд: знает свои лифты, делает batch-резолв имён в центральном API, кэширует имена, комбинирует, отдаёт фронту в loadAddress.

Контракт Address Service: batch-резолв ID → имена, глобальная версия имён, deprecated/terminated флаги. Версионирование контракта с первого дня.

Никаких прямых JOIN/FK между Tenant DB и Master DB в прикладном SQL — только через Address Service.

Реквизиты Master DB не попадают в тенантские конфиги.

2.2. Адресные ID (immutable identity)
ID адресов immutable, не переиспользуются, не удаляются (soft delete / is_active: false).

Переименование (дом «2/23» → «23», тот же объект) — ID сохраняется.

Сплит (дом 23 → 23/1 и 23/2): старый дом становится deprecated, лифты перепривязываются к новым домам, новые дома добавляются. Старые заявки остаются на старом ID.

Слияние: откладываем. При первом реальном случае — вернуться. Обязательство: ID не переиспользуются, заявки не переписываются.

Ошибочная привязка лифта: исправляется перепривязкой. Прошлые заявки в отчёт по новому дому не попадают; они всегда доступны по лифту.

Удаление: запрещено. Terminated лифт/дом остаются в системе.

2.3. Снимок адреса в заявке
В заявке хранятся и ID (city_id, street_id, home_id, object_id), и текстовый fullAddress.

Снимок в заявке не переписывается. Для открытых и закрытых заявок UI показывает снимок на момент создания.

Сервер собирает fullAddress из авторитетных имён на момент создания (через Address Service / кэш). Клиентский fullAddress — fallback при недоступности Address API. Рассмотреть два поля: клиентский и серверный снимок.

Отчёты строятся по ID-иерархии, не по тексту.

2.4. Отчёты и deprecated/terminated
Отчёты по дому — best-effort по текущей привязке. После сплита/перепривязки прошлые заявки в отчёт по старому дому не попадают.

Отчёты по конкретному лифту — всегда доступны, включая terminated лифты, за всё время.

Deprecated/terminated лифты не попадают в кэш loadAddress для фронта.

Для исторических отчётов фронт присылает отдельную команду «полный поиск, включая удалённые лифты» (в текущем API_PROTOCOL.md этого нет — надо добавить). Пользователь может посмотреть заявки по terminated лифту за прошлое время и информацию о расторжении договора.

2.5. Версия адресов и кэш
Фронт кэширует lift-home-street-city в IndexedDB.

Ключ кэша: per-user или per-organization (если передан org_key, кэш привязан к организации и компьютеру диспетчера).

При logout кэш не очищается — org_key ставит администратор организации на диспетчерском компьютере. У всех диспетчеров организации должно быть одно адресное пространство.

Видимость адреса в кэше не влияет на безопасность: если пользователю запрещено смотреть/менять заявку, сервер это не пропустит. Адрес в кэше — это справочник, не данные заявки.

Версия tenant-aware, считает тенантский бэкенд (комбинация глобальной версии имён + локальной версии лифтов/привязок).

Механизм инвалидации: notifications.versions + outdated (уже есть в протоколе). Нужно добавить address в versions.

Версия меняется при любом изменении состава или имён адресного набора организации, не только при изменении количества.

2.6. Лифты, группы, права
Лифт хранит привязку к группам (lift_id -> group_id). Не группа хранит объекты, а лифт знает свои группы.

UI массово привязывает/отвязывает лифты по улице/дому/городу к группам. Это массовая операция, не динамическое правило.

Привязка жёсткая и актуальная: если лифт убрали из группы A, пользователи без группы A теряют к нему доступ.

Перепривязка лифта к другому дому не меняет его группы.

История привязок лифта к группам не нужна.

Права проверяются по текущим привязкам лифта к группам (на бэкенде).

В будущем прав будет много (изменение полей описания, лифта, удаление/расторжение, привязка к механику-связисту, чтение всех полей и т.д.). PermissionService проектировать с запасом, не только role + три can_*.

2.7. Справочники (group/department/request/staff)
Для справочников выбран не снимок, а резолв на чтении:

переименовали — показываем новое имя;

удалили — не удаляем из БД, помечаем is_active: false.

Это осознанное отличие от адресов (где выбран снимок).

2.8. Офлайн (частично зафиксировано)
callNewOffline: пачки по 10, атомарность «всё или ничего», идемпотентность по offline_uuid.

Открытые вопросы по офлайну — см. раздел 4.

2.9. Валидация адресов при создании
Бэкенд проверяет существование object_id и собирает fullAddress из актуальных на текущий момент названий.

Проверка «лифт сейчас принадлежит этому дому» не должна отвергать корректные офлайн-заявки после перепривязки: IDs — исторический факт.

Политика при недоступности Address Service — см. открытые вопросы (раздел 4).

2.10. org_key и get_org_users
org_key — не совсем секрет: даёт возможность подгрузить имена диспетчеров в поле логина (datalist), чтобы им было достаточно ввести пароль.

Только после авторизации сервер отдаёт остальные данные.

Текущая модель check_org_key/get_org_users без доп. защиты — приемлема, но см. вопросы.

4. Открытые вопросы (требуют решения в новом чате)
4.1. Address Service
Точный контракт центрального Address Service: batch-резолв ID → имена, глобальная версия имён (одна или по сущностям: город/улица/дом), deprecated/terminated флаги. Версионирование.

Глобальная версия имён — одна на всё или по сущностям? Если одна, переименование улицы в другом городе поднимет версию у всех. При 4000 лифтах терпимо, но шумно. Если по сущностям — тенантский бэкенд считает max по используемым ID, точнее, но сложнее.

Кэш имён на тенантском бэкенде: TTL, инвалидация, batch-размер.

Политика деградации при недоступности Address Service: создание заявки с флагом «не подтверждён», асинхронная сверка, логирование.

4.2. Версия адресов

Ключ кэша IndexedDB: per-user или per-org. При org_key — per-org (компьютер диспетчера).

Поведение при logout: кэш не очищается. Нужно ли очищать при смене org_key? При смене пользователя на том же устройстве?

Механизм доставки версии: notifications.versions (polling 120 сек) + loadAddress.version на старте. Достаточно ли, или нужен отдельный лёгкий endpoint версии?

4.3. Terminated/deprecated в UI

8. Ключевые принципы (не потерять при переносе)
ID immutable, не переиспользуются, не удаляются. Soft delete везде.

Снимок адреса в заявке не переписывается. Сервер собирает авторитетный снимок; клиентский — fallback.

Отчёты по ID, не по тексту. По дому — best-effort по текущей привязке; по лифту — всегда.

Address Service — резолвер имён, не сборщик списка. Список собирает тенантский бэкенд.

Версия адресов tenant-aware, считает тенантский бэкенд. Доставка через notifications.versions + loadAddress.version.

Лифт хранит привязку к группам, привязка жёсткая и актуальная, история не нужна.

Справочники — резолв на чтении, soft delete. Адреса — снимок.

org_key — не секрет, но авторизация обязательна для остальных данных.

Аварийную заявку не блокируем при недоступности Address Service — принимаем с флагом.

PermissionService — с запасом под будущую матрицу прав.

ЧАСТЬ 1: Интеграция со Spult (XML API v4.1)


1. Идентификация автора и диспетчеров

• □ Сквозное текстовое логирование: Так как Spult передает реальное имя диспетчера из своей системы (например, Диспетчер Петрова), бэкенд в TicketService записывает это имя напрямую в текстовое поле original_author_name.
• □ Системный маркер ID: Поле original_author_id в Tenant DB для таких заявок принудительно заполняется предопределенным системным значением (например, 0 или 9999), указывающим на источник «Внешний шлюз Spult», чтобы разделять заявки из родного SPA и из XML.

2. Обработка неразрешенных адресов и создание «на лету»

• □ Создание лифта с уникальным ID: Если пришедший из Spult адрес не привязан к справочнику Master DB (отсутствует связь в lift_lkds_bindings по lkds_domain_id), автоматическое создание городов/улиц/домов запрещено. Однако для сохранения ссылочной целостности бэкенд создает в Tenant DB новую запись лифта с генерацией уникального локального object_id.
• □ Синхронизация идентификаторов: Данный object_id жестко связывается и мапится с внутренним ID лифта в системе Spult для последующих итераций.
• □ Таблица lift_unresolved_xml (Очередь разбора): «Сырой» XML-пакет, не прошедший валидацию адреса, и собранный на стороне Spult текстовый fullAddress сохраняются в специальную системную таблицу-очередь в Tenant DB (или Master DB).
• □ Админ-интерфейс «в один клик»: Проектирование структуры таблицы lift_unresolved_xml должно обеспечивать вывод списка таких инцидентов администратору для последующей ручной привязки лифта к авторитетному адресному дереву Master DB.

🔄 ЧАСТЬ 2: Отказоустойчивость, Деградация и Справочники


1. Логика отложенной валидации адресов (cron)

• □ Прием с флагом is_address_verified = 0: При недоступности центрального Address Service в момент создания заявки онлайн, бэкенд обязан бесперебойно принять тикет, записав в fullAddress текстовый fallback-вариант с фронтенда.
• □ Фоновый валидатор (Cron-скрипт): Разработка консольного скрипта, который с заданной периодичностью находит в базах тенантов записи с is_address_verified = 0, выполняет batch-запрос к восстановившемуся Address Service, перезаписывает fullAddress на авторитетный серверный снимок и выставляет флаг в 1.

2. Жизненный цикл справочников (Soft Delete)

• □ Резолв на чтении для архивных данных: Методы получения списков open и close на бэкенде при JOIN/резолве имен игнорируют флаг is_active для справочников (отделы, группы, механики). Это гарантирует, что даже если сущность отключена, исторические и текущие заявки корректно отображают ее название.
• □ Фильтрация в config: Метод config отдает массивы справочников строго с фильтром WHERE is_active = 1. Таким образом, фронтенд физически не сможет вывести отключенные группы или отделы в выпадающих списках (<select>) при создании новых или редактировании текущих инцидентов.

🔐 ЧАСТЬ 3: Безопасность, Интерфейс и Изоляция данных


1. Разделение валидации прав (Фронтенд vs Бэкенд)

• □ Интерфейсная роль на фронтенде: Роль пользователя (dispatcher, engineer и т.д.), приходящая в config, используется фронтендом исключительно как декоративный инструмент для переключения экранов, сборки меню и удобного отображения кнопок.
• □ Жесткий серверный ACL (Access Control List): Бэкенд полностью игнорирует любые утверждения фронтенда о правах. Каждый входящий API-запрос на изменение данных (calledit, callClose, callnote) проходит сквозь независимую серверную проверку в PermissionService на основе сессии и реальной роли пользователя, хранящейся в БД. Передача лживых данных со стороны клиента архитектурно исключена.

2. Инфраструктурная изоляция на уровне СУБД

• □ Пользователь Master DB: Для работы центрального ядра создается выделенный пользователь СУБД. Его привилегии жестко ограничены доступом только к Master-таблицам (организации, глобальные адреса). Он не имеет прав администрирования.
• □ Пользователь Tenant DB: Для подключения к базам данных организаций создается отдельный изолированный пользователь СУБД. В целях безопасности данный пользователь физически лишается любых прав (включая SELECT и GRANT) на таблицы Master DB. Даже при компрометации тенантского PHP-кода злоумышленник не сможет получить доступ к центральной базе и данным других клиентов.
